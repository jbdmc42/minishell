Suggested implementation order (easy → hard)
-------------------------
1) Exit status propagation & support for commands with '/'
   - What: Make parent set shell->exit_status from child waitpid status and allow executing absolute/relative paths (strings containing '/').
   - Why: Small correctness fixes that make external execution behave like a normal shell and provide correct $? for scripts/tests.
   - Effort: Very small (minutes → 1 hour).
   - Files: `commands_extra.c`, `commands.c`, `main.c` (where shell->exit_status is used).

2) Implement `unset` builtin
   - What: Remove environment variable node from linked list and free memory; handle invalid identifiers like export/unset rules.
   - Why: Completes builtin set and allows tests that rely on unset.
   - Effort: Small (1–2 hours).
   - Files: `unset.c`, `export_helpers.c`, `minishell.h` (if helpers needed).

3) Variable expansion core: $VAR and $?
   - What: Implement replacement of $VAR by its value from env list and $? by shell->exit_status. Do this during token processing (before building argv for execution). Handle missing variables as empty string.
   - Why: Required for correct command arguments and many scripts.
   - Effort: Medium (2–4 hours).
   - Files: `parsing.c` / `tokenization.c` / `utilities_two.c` (helpers), `commands.c` (ensure builtins get expanded args).

4) Double-quote handling for $ (expand in double quotes, not in single)
   - What: Ensure tokens parsed from double quotes still undergo variable expansion, while single-quoted tokens do not.
   - Why: Shell standard behavior, ties into variable expansion implementation.
   - Effort: Small → Medium (1–3 hours) depending on token pipeline.
   - Files: `parsing_helpers.c`, `quote_handling.c`, expansion helpers.

5) Build command structures (attach args + redirections)
   - What: Convert token list into a simple command list/struct: command name, argv array, list of redirections, and pipeline linkage.
   - Why: Needed to implement redirections and pipes cleanly.
   - Effort: Medium (3–6 hours).
   - Files: new command struct file or modify `parsing.c`, `tokenization.c`, `commands.c`.

6) Basic redirections: >, >>, < (single-command)
   - What: For each command struct, handle output truncation (>) and append (>>) and input redirection (<) by opening files and dup2 in child before execve. Handle error messages like bash.
   - Why: Common feature; relatively self-contained once command structs exist.
   - Effort: Medium (3–6 hours).
   - Files: execution path in `commands.c`, helper fds management file.

7) Heredoc (<<)
   - What: Implement heredoc reading to a pipe (or temp file), respect quoted/unquoted expansion rules, do not add heredoc lines to history, and connect pipe to child's stdin.
   - Why: More complex due to interactive read and expansion rules.
   - Effort: Medium→High (4–10 hours).
   - Files: new heredoc helpers, `parsing_helpers.c`, `commands.c` execution.

8) Pipes (single and multiple)
   - What: Create pipes between commands, fork children for each command, dup2 appropriate fds, close unused fds, and wait for all children while collecting exit statuses.
   - Why: High-priority feature; coordination-heavy and bug-prone.
   - Effort: High (6–20 hours depending on polishing, signals, edge-cases).
   - Files: execution core in `commands.c` / new `executor.c`.

9) Complete redirection + pipe integration
   - What: Ensure combination cases (pipes + redirects + heredoc) behave correctly, correctly preserve/restore fds for builtins executed in parent when needed.
   - Why: Required for real-world correctness.
   - Effort: High (several days of careful testing).
   - Files: `commands.c`, `executor.c`, redirection helpers.

10) Memory management & leak fixes, tests
   - What: Free tokens, command structs, temporary buffers, and validate with valgrind or similar. Add regression tests to compare with bash for typical cases.
   - Why: Stability and final polish.
   - Effort: Medium (several hours to days depending on leaks found).
   - Files: `cleaning.c`, all modules.

General notes and ordering rationale:
- Implement items that change small, localized code first (exit code propagation, support for '/'), so you get immediate visible improvement and smaller review surface.
- Then finish single-command builtins/features (unset, expansion) — these unblock tests and reduce complexity when later wiring multiple components together.
- Next create a clear command representation (step 5). Having a command struct drastically simplifies redirections and pipes implementation.
- Do redirections before pipes if you prefer smaller incremental steps; pipes require command structs anyway but redirections are easier to test on single commands.
- Heredoc is trickier because of interaction with readline and expansion rules — treat it after simple redirections.
- Pipes and multi-process coordination are the heaviest—do them last and test each stage thoroughly.

Testing strategy (short):
- After each completed task, write 5–10 basic cases comparing output and exit codes with bash for that feature.
- Use small helper scripts and run them repeatedly while developing (capture stdout/stderr and exit codes).
